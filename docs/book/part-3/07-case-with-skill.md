# 07 案例（上）：用现成的交付模型做官网

<p class="lead">假设你也想给自己的产品做一个像 canvasagents.dev 那样的演示官网，而且已经有人把这类官网的交付模型总结好了。你会发现：定义正确，简单到只剩一句话。</p>

## 需求

你有一个产品，想做一个官网。不是那种「左边一句标语、右边一张截图」的模板页，而是像 [canvasagents.dev](https://canvasagents.dev) 那样：往下一滚，镜头一镜到底地带着访客走过产品的真实界面，一幕一幕演示产品怎么解决问题。

## 先说「交付模型」长什么样

第 6 章说，成为 AI Native Builder，就是能为一个需求构建出它的交付质量三角模型。如果这个模型已经有人构建好了，你直接拿来用就行。

那一个交付模型，拿在手里是什么样子？**从现阶段来看，它对外的表现，就是一个 Skill**：一份交给 Coding Agent 的说明书，加上模板和脚本，规定了 AI 应该按什么路径去调度、做到什么程度算对、怎么验证、出错了怎么办。换句话说，**Skill 就是一条写下来的 AI 调度路径。**

做产品演示官网的这个交付模型，我把它整理成了一个 Skill，叫 **product-demo-site**，可以在[附录 A](/book/appendix/skill) 下载。

## 三角模型，几乎是现成的

### <span class="edge-define">定义正确</span>：只需要一句话

第 6 章说过，定义正确最快的捷径是**找到一个符合期待的样本**。一个现成的交付模型，就是一个已经拆解好的样本：怎么讲、讲几幕、首屏放什么、字幕写几行、怎么验证，全都写在里面。

所以你要给它的，只有两样：

1. **这个交付模型**（product-demo-site）；
2. **你的产品资料**：一个产品链接，或者产品的代码库。

然后说一句：

> 用 product-demo-site 给我的产品做一个演示官网：{你的产品链接}

剩下的「定义」工作，Agent 自己去做：

- 打开你的产品，截下真实的界面；
- 读出产品自己的配色和字体；
- 读一遍首页和文档，起草一份方案：一句话承诺、演示哪几个场景、每一幕对应哪个界面、怎样算做好了。

你要做的，只是**审一遍这份方案**。

### <span class="edge-verify">验证正确</span>：一条命令，加上看图

你知道它要做成什么样，所以完全可以验证：

- **机器**：一条 `pnpm verify`，在电脑和手机两种宽度下逐幕截图，自动检查字幕、溢出、报错、读屏、减少动态效果；
- **Agent 自己看图**：逐张看截图，找机器发现不了的问题；
- **你**：最后在真实设备上按标准走一遍。

### <span class="edge-recover">失败可恢复</span>：可回滚，加回流

部署到能一键回滚的地方，上线后在几种常见浏览器里抽检。出了问题，修好之后，把它变成下一次的检查项。

## 实录：这本小册的官网

这本小册的[官网](/landing/index.html)，就是用这个交付模型做出来的。全过程只有一轮：

1. **一句话开始。** 我对 Agent 说：用 product-demo-site 给这本小册做一个演示官网，小册在本地这个地址。
2. **Agent 自己研究。** 它打开小册，截下了 6 个真实页面：首页、第 1 章、第 5 章、第 6 章、第 7 章、第 8 章，浅色、深色各一套。它还读出了小册自己的配色：米白的纸张底色、墨色正文、朱红色主色、衬线标题。
3. **起草方案，我审一遍。** 方案是：按小册自己的顺序，镜头依次走过这 6 页（是什么、为什么、怎么成为，再到两个案例），每一页推近到最关键的一段，配一句标注，最后拉远，看到整本书的主线。
4. **生成和验证。** 自动检查全部通过；Agent 看截图时顺手修掉了几处小问题，比如手机上推近后字太小。
5. **人工验收，完成。**

## 有交付模型和没有交付模型

| | 有交付模型（这一章） | 没有交付模型（下一章） |
| --- | --- | --- |
| 什么是对的 | 一句话 + 产品链接，Agent 起草，人审一遍 | 并行试了三个方向，转了好几圈才说清楚 |
| 怎么证明对 | 一条命令 + 看图 + 人工验收 | 目测、手写测试，靠人兜底 |
| 出错了怎么办 | 回滚流程和抽检清单已经写好 | 在别人的设备上踩坑后再补 |
| 耗时 | 一次对话 | 约 6 周、45 个提交 |

用现成交付模型的人用得很轻松。但你不能指望每个需求都有一个现成的交付模型。
